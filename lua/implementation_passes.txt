Implement Control Layer System
    Implementation checkpoint: JSON Control Layer, compiler/runtime/editor, timeline/display adapters,
    owned keypads, RBMK/DFR operator/VMF migration and rebuilt BSPs are implemented.
    Static/runtime-fixture checks pass; real rebuilt-map acceptance remains pending.
    This pass stays here until those workflows are verified; foundation-0.1 is unchanged.
- Control Layer is the wrapping interface system or a manager that will binds hammer interactable entities (func_button, func_rot_button) intended as controller of Luasquare entities. It is the interface between players + external controlling components and an acting component.
- Goal is to increase robustness of controller map-entities and actually physically locking/unlocking them instead of the current rejection method.
- Control Layer can lock/unlock button when they become unavailable/available, protecting it from actual player (Or other non-player entities capable of pressing map button such as LambdaPlayers).
- Control Layer can press, pressIn/Out or toggle button when prompted by other systems such as Timeline (Will be important in later automated sequences).
- When a control is prompted to press through control layer system but it is locked, keep the request for a 2 seconds, pressing again immediately after it is unlocked, if it doesn't unlock in 2 seconds, request expires.
    - This is to prevent pressIn/Out failure on same-tick unlock and interaction request.
- ANY control interaction (including automated smart control system in the future) SHOULD be routed through the Control Layer before the control signal reaches the real acting component. this system shall reduce the validation hits by locking the control before it can even get activated and actually sync the button lock state in the map so that map button can have 'locked' feedback to player.
    - Few exception cases are automating variable numeric inputs from modules such as keypad_controller. (Control Layer triggered by automated module such as timeline can submit value directly without pressing actual keypad)
- Control Layer can print logs for blames (who used this control and when in server HH:MM:SS eg. [11:30:02 LadevAsta] Turbine A: TRIP (Red Highlight) / [16:11:39 DECAOS] Coolant Pump 3: SPEED 3 > 2 (No highlight)).
- Control Layer editor with func_button and func_rot_button auto-detection following shared naming convention: 'CTRLI_buttonname' CTRLI (Control Interface) in capital and buttonname in any-case.
- Bypassing the control layer is discouraged as it will cause unsync problem with the state of the real map func_buttons that is a toggle (eg. 2-state levers).
- Pressed button workflow
  - Always make other system tell the control layer to press the actual button it wants to. By this way, it will not just simulate it.
  - Player or Automated Control System (Activator) want to press the button
  - Activator press the button, the button (func_button) will have defined with control layer call.
  - This button's control layer will provide who this button is, and who activated it.
  - The control layer receives interaction and call for action on actor component with provided context.
- Locking button example workflow
  - There are too much Annihilation fuel in the tank. The ennabled auto control system (Activator) wants to pressOut and Lock the button that fill it which is a toggle button.
  - Activator send pressOutLock request to control layer, telling who to lock.
  - Control layer pressOut and shortly lock the fill button.
  - This defined button also have a special env_sprite indicator to indicate when it is locked, Control Layer also send ShowSprite fire to the defined env_sprite.
    - This is because func_button don't have OnLocked output!
- Action of the func_button in hammer will have it defined in RunPassedCode as calling the control layer.
  - func_button may also have additional call natively called in hammer but it is recommended to only have one RunPassedCode for control layer and the remaining for additional hammer-native fires.
- Control Layer shall be used for player-interactable buttons and 3d2d display with interactables, not things that are not intended to be exposed to player interaction.
- Control Layer is map-specfic, it is registered with controls and its action.
  - Press
  - Toggle
  - Keypad (numeric)

Implement new Catalyzer manual/auto control and flow model
- (multi-)SELECT[1-6] AND SELECT MODE > PRIME > CHARGE > EXCITE > FIRE
- Many func_button > func_rot_button > func_rot_button > func_rot_button > func_rot_button
- Detailed Flow :
    - Select all catalyzer that applies AND Select mode (Annihilation or Catalyze)
        - In Pre-Annihilation, ALL catalyzer must be selected at Annihilation, but PRIME is already unlocked with at least one selected.
            - Operator MAY select less than 6 but the lesser will risk annihilation failure and must redo the fire.
            - This intentionally opens a window for operator error.
            - Automated system always select 6.
        - In Pre-Darkfusion, ALL catalyzers must be selected at Catalyze before PRIME is even unlocked.
        - In Darkfusion-Active Fuel Cycle, At least one catalyzer must be selected before PRIME is unlocked.
        - In Darkfusion-Passive Fuel Cycle, All catalyzers are selected and enforced by default.
            - When Passive Fuel Cycle has just been activated (or switched to), PRIME, CHARGE, EXCITE, FIRE must be done then the Passive Fuel Cycle is successfully initialized.
            - By then, PRIME, CHARGE, EXCITE and FIRE is switched back to PressOut position then be locked.
    - PRIME selected catalyzers, immediately locking selection buttons in the process then lock itself upon activation, run alerting timeline on selected catalyzers.
    - CHARGE selected catalyzers, Locked Prime lever (and itself, it will remain in pressIn position), run charge timeline on selected catalyzers 'charge' involves the CatalyzerHull firing laser, glowing sprite and playsound but not the Tip.
    - EXCITE selected catalyzers, Locked Charge lever (and itself), run excite(formerly known as charge_high) timeline on selected catalyzers 'excite' involves the CatalyzerTip emitting glowing and progressively growing sprite to the max size. By then timeline shall tell that FIRE should be available.
    - FIRE selected catalyzers, Locked Excite lever (and itself), run fire timeline on selected catalyzers 'fire' involves CatalyzerTip activating beams(for darkfusion or annihilation), enlarging both CatalyzerHull and Tip glowing sprite from their latest size.
    - After FIRE, all levers unlock and immediately return to PressOut position before locking again as fast as possible. Then, unlock selection button group again.
- Cancel lever is only available from Prime through Excite where it will discard the charged energy (also clear fired timeline).

Implement Luasquare Audiosystem. [Implemented]
    - Subtitler.
        - Subtitler will draw a box and text on player's hud when this player heard a sound somewhere that have defined a subtitle with this system.
        - Box and text will fade in and animated with subtle 'slide up'.
        - The text will fade away after the sound is stopped (query sound duration before showing and fading.)
        - Box will fade away and animated with subtle 'slide down' when there are no text displayed.
        - If there are another subtitled sound coming up while another text is taking place in the subtitle box, it pushes up the previous text and expand box as needed.
        - There can only be client-configurable 3 subtitle text on the box, the oldest text above limit is fade away immediately.
        - Think of it being very similar to Half-Life-2 subtitles although is lua addon-native and easily moddable.
        - Some subtitle text can be special (Being red text, bold text, overridden font and size, animated glitchy effect.)
        - Subtitle can have speaker's name, show as [speaker's name]: [defined line]
    - Regulated Soundwave (AKA. Background Music controller)
        - This system can be told by other component to play/pause/regulate/stop background music to the player's ear. Sound will be affected by both game's volume setting and its own volume slider.
        - Active subtitled sound will immediately reduce 'music' volume by a percentage. (Behavior can be disabled optionally)
        - Music played via Regulated Soundwave system may be different from how sound from ambient_generic are handled? (The ones thats not affected by DSP)
            - So they could get paused properly or even speed up or slow down while they are playing if possible.
        - Music pauses when the system detect that the server is paused or singleplayer game pause, to prevent most-probable accidental auditory timeline desyncs.
            - If possible, detect if server timescale is altered where it attempt to slow down or speed up the soundtrack, may be pitching it in the process.
    - Intercom (Facility PA)
        - Sounds not intended as map intercom or PAs.
        - Use case for facility PAs (eg. DECAOS)
        - Support sounds that is intended to play globally as well similarly to ambient_generic. (Sound that physically exist, affected by DSP unlike music.)
        - May create a 'channel' (Used with PA). Sound would play in a channel.
        - PA sound channel flow :
            - From 'silence', When a voiceline is to be played, it will first play a tone first. Then a voiceline is played.
            - If there is another voiceline has to be played while another is playing, if the priority is higher, interupt current voiceline and play interrupt tone then play this voiceline.
            - Once voiceline end, after 2 seconds it will consider 'silence'.
    - Extra ambient controller
        - Sound that is not a music or intercom
        - Sound that is globally played just as ambient_generic and affected by DSP (Reactor mechanical roars on demand)
        - Can also be used to handle any localized sound at a position on demand although this is not the main use.
    - Soundscape controller
        - This simple system directly interface with map's named env_soundscape.
        - State-based system. When a state is told, it switch there and disable all connected soundscapes and enable soundscape for that state.
        - Affect all env_soundscape with same name.
        - This is because different part of the map should have different set of soundscape and trigger area.
